Integrations · LTI 1.3

LTI 1.3 and LTI Advantage, checked claim by claim.

EducateOS acts as an LTI 1.3 tool, so a teacher can launch an EducateOS activity from any LMS that speaks LTI 1.3, including Canvas and Schoology. This page lists what the tool code does, and the status of each part.

SupportedWhat the statuses mean
OverviewLTI 1.3CanvasGoogle ClassroomCleverOneRoster and ClassLink
Sync directionLaunches and rosters come in from the LMS. Approved scores go out to it.
Source of recordThe LMS is the gradebook of record only for classes the district routes grades to. Rosters from NRPS apply only where the district names the LMS as the source of enrollments.
Data it carriesOnly the platform's user ID (sub), the course and the resource link. Names, emails and roles in the token are ignored.
Tool-side LTI 1.3 and LTI Advantage features
FeatureWhat it doesStatus
OIDC third-party loginAccepts iss, login_hint and target_link_uri, plus optional lti_message_hint, client_id and lti_deployment_id, by GET or POST. State and nonce are single-use 256-bit random values that expire after 10 minutes and are stored in the district's Durable Object. The browser is bound to its login by a partitioned __Host- cookie, or by LTI client-side postMessage storage where cookies are blocked.Supported
id_token validationRS256 only, verified against the platform's keys. Checks iss; aud, and azp when there are several audiences; exp and iat (10-minute maximum age, 60-second clock skew); nonce; deployment_id; message_type; version 1.3.0; and target_link_uri. EducateOS reads only sub, context.id, resource_link.id and its own custom link ID.Supported
Platform JWKS and key rotationFetched without following redirects and cached for 10 minutes. An unknown kid triggers a refetch, at most every 30 seconds, so a platform's key rotation is picked up. RSA keys under 2048 bits are skipped, and a token with no kid is refused. Canvas's keys verified live; a platform-side rotation wasn't exercised in the run.Supported
Tool keysRS256 2048-bit keys published at /lti/jwks. The key set is stored in the district, and an administrator's rotation keeps the previous public key published; a rotation passed live against Canvas. Scheduled rotation isn't built yet.Supported
Deep Linking 2.0Returns ltiResourceLink items in a response JWT signed by the tool, up to 50 at a time, honoring accept_multiple. Canvas accepted the tool's signed response, and a student's launch of the placed item opened the chosen activity. Selected items don't yet create a gradebook column.Supported
AGS: line items and resultsLists line items (filtered by resource link, resource or tag), reads and creates them, and reads results. Access tokens come from client credentials with a signed JWT assertion. A token that grants fewer scopes than requested is refused. Creating a line item in the Canvas gradebook passed live; listing and results reads are unit-tested only.Supported
AGS: teacher-approved score passbackA score is posted only if the class routes grades to the LMS and a teacher's approval matches that exact student, column, version, score and maximum. The approver must still teach the class, and the student must still be enrolled. Each score posts once, and a failed send can be retried.Supported
NRPS: names and rolesMembership v2.0, following Link: rel=next paging up to 10,000 members. A partial roster is never applied. Members are matched to people through identity links, roles come from the district rather than the LMS, and members who drop become inactive rather than deleted. A Canvas roster read passed live, without paging. Known gap: next-page links are checked by origin but not yet by path.Supported
Dynamic RegistrationBy invitation only. An administrator creates a single-use invitation that lasts one hour. The platform's registration then waits as pending until an administrator approves it with a provider and at least one class mapping, adding the deployment ID if the platform creates it only at install, as current Canvas does.Supported
Launch to person and classA launch maps to a person by (district, issuer, sub) through an identity link an administrator approved, never by email. An unknown user sees their issuer and subject to give an administrator, and no account is created automatically. Each LMS course maps to one EducateOS class, set by an administrator. A launch from an unmapped course is refused.Supported
Served by the district WorkerThe district's Worker serves the LTI endpoints at /lti/, open to LMS users without the district's sign-in; the administrators' settings stay behind it.Supported
EducateOS as an LTI platformLaunching trusted third-party LTI tools from inside EducateOS, with scoped rosters and approved grade services.Planned

EducateOS claims no 1EdTech certification. "LTI 1.3" and "LTI Advantage services (Deep Linking, AGS, NRPS)" describe the specifications the code is written to, not certified conformance.

Failure modes we test for

  • A replayed login state, or a reused nonce with a fresh state.
  • A wrong audience, or several audiences with no azp.
  • An expired, not-yet-valid, future-dated or too-old token.
  • An unknown deployment, or one that differs from the login's.
  • A forged or altered signature, alg: none, or an HS256 token.
  • A token from a different registered platform, or a launch into another district.
  • Spoofed role, name or email claims, which are ignored.
  • A platform's key rotation, and a withdrawn key.
How we validate. Every status on this page comes from the project's maturity record. Unit-tested features run against fakes that behave like the real service: the fake LTI platform, the district stores on workerd. A feature moves to "Validating against live sandbox" when a run against the vendor's own sandbox is under way, and to "Supported" only after it passes there. More on our testing →
