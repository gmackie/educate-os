Product and data model for the full onboarding experience

The current intake prepares a request locally and stores its edited text in the existing per-user session draft mechanism under a separate teacher-onboarding scope. The home draft is preserved. Preparing the brief does not create a workspace or send a model request; sending or using a workspace-backed attachment/connection control follows the existing workspace flow. Draft text can resume in the same browser session; files and unsent intake selections are not a cross-device onboarding record. A future resumable record should belong to the teacher first, with an optional school class association. Keep credentials in existing gatekeepers and student identity in the district directory.

A future source inventory should record origin, version or digest, content type, owner/rights, visibility, extraction status and supported transformations. Imported content is evidence for a proposal, never agent instructions.

The prepared request asks the existing AI workspace to compare quick reuse, a native activity and a connected app, leading with the teacher’s preferred option. It asks for source evidence, effort, limitations and required access, and asks the AI to wait for the teacher’s selection before building. This is an editable request, not a dedicated or guaranteed proposal engine. Existing capability and action-approval mechanisms remain the authority boundary.

Use existing Content Studio and cartridge jobs rather than a parallel publishing pipeline. Attach generated activities and apps to the same class context. Account consent, a content review, publication and approval of an external write remain distinct decisions.

Goals, boundaries and acceptance

Goal: a teacher can explain what they have, choose a useful integration depth and finish one lesson without rebuilding their whole classroom.

Initial boundary: personal preparation requires an existing authenticated Workshop account, not district enrollment or an assigned class. Deployment sign-in policy still applies. School-managed publishing requires school access. Self-serve school-class creation, universal conversion, ongoing sync and cross-device progress are not implemented.

Full-flow acceptance: begin from existing teacher-owned materials, retain source evidence and rights, offer useful alternatives, preserve private notes, review the student experience and launch only the teacher-selected result. Measure first reviewed material and first assigned lesson; do not send student content or source documents to product analytics.

Risks and mitigations
  • Promise exceeds adapter support: display a per-source support result before confirmation; report skipped content and fidelity loss.
  • Unintended publication or external writes: draft by default; separate review, publish and external action approval.
  • Missing or excessive authority: preserve district enrollment checks and connector capabilities; never infer access from an imported roster or email address.
  • Generated lesson loses intent: cite original passages, preserve rubrics and answer keys, show editable differences and student preview.
  • Large or interrupted migrations: resumable batches, dedupe, partial-success reporting and source retention.
Open decisions
  • Audience resolved: individual teachers bringing existing materials. A personal workspace is the default; school enrollment and student access remain separate.
  • Choose the first structured source adapter from actual teacher inventories. Document fidelity, source citations and Drive folder selection are candidates beyond existing generic attachments and connectors.
  • Keep original source systems authoritative for roster and official grades unless the school explicitly changes that choice.
