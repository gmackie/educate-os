EducateOS: one domain per district, admin.educateos.io, and the web + mobile design Approved 2026-10-28

2026-10-28 · gmackie/educate-os · branch SCHO-254-mobile-working · follows SCHO-254 / SCHO-256

Recommendation: each district gets one hostname (<slug>.educateos.io or its own domain). That host serves the LMS at / and the AI workspace at /ai, behind one Cloudflare Access app and one identity keyed by Access sub. Separately, admin.educateos.io is the operations console for the districts that opt in. It is built from the same educateos-admin package (Worker + D1) that the open-source edition deploys into the district's own account.

The phone error you saw comes straight from today's split. The phone holds an Access token for schoolos.gmac.io and sends it to the district host. Access in front of that host doesn't accept it and answers with a 302 to its login page, which the app's redirect: 'error' turns into "fetch failed". Once there is one host and one Access app, that class of bug can't happen.

1 · What's broken today, and why

"fetch failed: Redirect is not allowed…" Root cause found

  • Sign-in on the phone goes through the Workshop (schoolos.gmac.io). The Workshop gives the phone its own Access JWT, so aud is the Workshop app (workshop-backend/src/server.ts:1050).
  • DistrictClient then calls the district host (district.schoolos.gmac.io / northfield.educateos.io), sending that JWT as a header and as a CF_Authorization cookie (apps/mobile/src/api/client.ts:27-35).
  • The district Worker would accept the token, because its CF_ACCESS_AUD lists both audiences. The request never gets there: the district host's own Access edge checks the cookie against its own AUD and sends a 302 to the login page.
  • Expo's native fetch throws FetchRedirectException on any 3xx when redirect: 'error' is set, and the raw text reaches the screen.

About 85% confident, from the code and the runbook; I haven't reproduced it against the live host yet. Step 0 below confirms it with one curl.

AI tab dark, the rest light Root cause found

  • The mobile app has one hard-coded light palette (apps/mobile/src/theme.ts), even though app.config.ts sets userInterfaceStyle: 'automatic'.
  • The AI tab is a WebView of the Workshop (screens/Workspace.tsx:111). The Workshop follows the OS, so on a dark-mode phone it renders dark.
  • On the web the theme drifts too. The Workshop uses its own theme code and the key gadgets:theme-mode; the LMS UIs use @gadgets/ui/theme with educateos:theme-mode, on a different origin. The admin UI's CSS is missing the @custom-variant dark line.
The underlying design problem: two products on two hosts with two identities
  • Hostnames today: the Workshop's router serves schoolos.gmac.io. The district Worker serves district.schoolos.gmac.io plus the alias northfield.educateos.io. The five demo districts are district Workers only, with no AI workspace. The router never sends anything to the district (packages/router/src/index.ts:47-80).
  • Identity: the Workshop keys users by Access email (no PRINCIPAL_RESOLVER is bound). The district keys them by Access sub (ADR-0003). Each host has its own Access app and AUD.
  • Links between them: the Workshop reaches the district only through the gatekeeper-educateos "School" iframe. The district UIs never link to the Workshop. The web LMS has no AI entry point; the student aiHelp flag is a placeholder.
  • Installer: it already attaches <slug>.educateos.io to the router and binds the district as an optional service ("nothing in the instance routes to it yet", district-worker/src/worker.ts:94-98). The installer is already halfway to the one-host model; the demo deployments aren't.
  • Phone setup: the QR codes are typed in by hand on mobile.educateos.io/pair, and no web app links to that page. Manual setup asks for two raw URLs (portal and workshop). The app has no QR scanner of its own. Access JWTs can't be refreshed and can't be revoked per device. Android app links aren't verified.
  • Admin: educateos.io/app is a read-only installations list with health probes and a guided install. It has no users, devices, Cloudflare analytics or release management. No deployed Worker uses D1, and nothing calls the Cloudflare GraphQL Analytics API.

2 · Goals and non-goals

Goals

  • One district = one origin = one Access app = one identity (sub). The LMS and the AI workspace share sign-in, theme, navigation and the user menu.
  • A custom domain works the same as <slug>.educateos.io.
  • Setting up a phone takes a scan from the web app: no typed URLs, no second password.
  • Phones carry district-issued, device-bound credentials that refresh on their own and that an admin can revoke one by one.
  • admin.educateos.io manages workspaces (health, Cloudflare stats, releases, domains), users and devices for the districts that opt in.
  • The open-source edition ships the same admin as its own Worker + D1 in the district's account and needs nothing from educateos.io.
  • One design system (Kumo + @gadgets/ui) and one theme preference across web, the AI workspace and mobile.

Non-goals (this plan)

  • Rewriting the AI workspace as native mobile screens. It stays a themed WebView.
  • Merging the Workshop and district Workers into one Worker. They stay separate Workers behind one router.
  • Moving district data into educateos.io. The hosted admin stores metadata only (ADR-0001).
  • Billing UI and the marketplace (SCHO-208 owns those).
  • Replacing Cloudflare Access as the web sign-in front door.

Identity: one principal per person
  • One Access app per district host, so one AUD. Both Workers verify the same JWT. The district's dual-AUD allowance (access.ts:19-23) is removed.
  • The Workshop binds PRINCIPAL_RESOLVER to the district (the seam from ADR-0003 already exists), so its user Durable Object is keyed principal:<id> and no longer by email.
    Migration: a one-time map from email-keyed DOs to principal-keyed ones, done for Northfield's existing users. The demo districts have no Workshop users yet.
  • The AI workspace knows the user's role and classes from the district principal. "Ask AI about this assignment" passes context through a link (/ai/new?context=assignment:<id>). It's checked again on the server, never trusted from the URL.
  • Workshop password tokens remain only for open-source installs that run without Access. Phones never use them.

  • When features.ai is off, /ai shows an "AI isn't enabled at your school" page rather than a 404.
  • The AI budget meter from the guard ledger shows in the header for staff.

One theme system

  • Use @gadgets/ui/theme everywhere. Remove the Workshop's own theme.ts/ThemeContext and keep only its accent override.
  • One key, educateos:theme-mode, on one origin, so a change applies everywhere at once.
  • The district brand accent comes from the manifest, through applyAccentColor.
  • Fix the missing admin-ui @custom-variant dark. The Workshop's violet dark palette becomes a set of Kumo tokens.
Web "Connect phone" page (user menu → Connect phone, plus a one-time banner after first sign-in)
  1. The page creates a pairing room on the district: POST /api/pair/rooms, signed in with Access. The room lasts 2 minutes and holds one phone.
  2. It shows a QR code for https://mobile.educateos.io/j#o=<district origin>&r=<room>&s=<secret>, plus App Store and Play links for people without the app.
  3. The phone scans it, claims the room with its P-256 public key, and both screens show the same 8-character code.
  4. The user checks the codes and clicks Approve. The district registers the device, mints its credential, seals it to the phone's key, and leaves it in the room.
  5. The phone collects and decrypts it. The page then shows "Ava's iPhone 16 is connected" and a link to Your devices, where the user can rename or sign out each phone.

This is the existing SCHO-256 protocol (ECDH + HKDF + AES-GCM, code comparison) moved from mobile.educateos.io onto the district itself, so the runtime keeps working with educateos.io offline. mobile.educateos.io keeps only what can't move: AASA/assetlinks, the universal-link landing page, and a "get the app" page.

  • Teacher: Today · Classes · Review · AI · Me
  • Guardian: Family · Calendar · Inbox · Me

  • Me: profile, devices, theme, notifications, switch school, sign out, delete account (App Store guideline 5.1.1(v)).

Look and feel

  • theme.ts gets light and dark palettes generated from the shared Kumo tokens; useColorScheme() follows the system unless the user overrides it under Me.
  • The AI WebView is injected with data-mode and the accent before load (injectedJavaScriptBeforeContentLoaded), and updated live when the theme changes.
  • School branding (logo, accent) comes from the manifest.
  • Replace the hand-rolled stack with expo-router to get native back gestures and deep links (/class/:id, /assignment/:id).

Reliability

  • Every API call goes to /api/m/* with a device token. A 401 refreshes silently; a revoked device goes to a "This phone was signed out by your school" screen.
  • redirect: 'manual'. Any 3xx becomes a typed needs-sign-in error with a friendly message; raw fetch text never reaches users.
  • Push: content-free alerts ("You have 2 updates"), sent by the district through APNs/FCM. The phone fetches the details itself.
  • Android assetlinks.json published; autoVerify passes.
Device credential design (district-issued, device-bound)
  • Registry (district DO, new table devices): id, principal, label, platform, model, app version, P-256 public key (JWK thumbprint), created, last seen, last country, push token, status (active | revoked), revoked by.
  • Tokens: a 15-minute access token, plus a refresh token that rotates on every use (if a refresh token is reused, the device is revoked). Both are bound to the device key: each request carries a short-lived ES256 proof over method · path · ts · token hash, in the style of DPoP.
  • Access: /api/m/* is an Access bypass path. The Worker enforces device auth on every route under it and shares the authorisation code with the web API, so the policy floors from ADR-0004/0010 apply the same way.
  • Revocation: takes effect immediately, because every request checks the registry. "Sign out everywhere" revokes all of a principal's devices, and suspending a user does too.
  • Private key: stored in SecureStore (WHEN_UNLOCKED_THIS_DEVICE_ONLY). Moving to the Secure Enclave / StrongBox through a small native module comes later.

6 · admin.educateos.io (and the open-source admin)

One package, two editions Recommended

  • New package packages/educateos-admin: a Worker with D1, a Kumo SPA and Access sign-in.
  • Hosted: admin.educateos.io in the EducateOS account. It manages many workspaces from districts that opt in. It replaces educateos.io/app, which then redirects; /clever/launch and /registry/v1/* stay on educateos.io.
  • OSS: the installer adds admin as its own Worker + D1 in the district's account (default admin.<district domain>), managing one or more workspaces in that account.
  • Both editions talk to districts only through the signed /api/ops/* API, so they share one code path and one test suite.

What lives where

  • District /admin (in the LMS): academic administration: roster, classes, guardians, curriculum, policies, AI budgets, term rollover. Used by school staff every day.
  • admin (either edition): operations: workspaces, health, Cloudflare stats, releases, domains, sign-in methods, users and devices, audit.
  • D1 holds: operators, workspace registry, ops-key pairs, cached analytics snapshots, and an audit log of admin actions. It holds no student records.
  • Data the hosted edition never stores: user lists and device details pass through live from the district. Only counts and aggregates are cached.

Token: the district holds a read-only token (Account Analytics Read, Access Audit Logs Read, Workers Scripts Read) as a secret. /api/ops/analytics runs the queries, caches them for 5 minutes and returns aggregates. The hosted admin never holds a district's Cloudflare credentials. The guided install asks for this token through a prefilled token-creation link.

Signed ops API: how an admin edition talks to a district
  • When a workspace is enrolled (an opt-in step in district /admin → Operations), the admin edition's Ed25519 public key is registered with the district under scopes such as health, analytics, directory:read, directory:write, devices and releases. This reuses the educateos-fleet registration and rekey protocol.
  • Each request is signed over method · path · body-hash · ts · nonce and carries the acting operator's identity. The district checks scope, nonce and age (±60 s), and records the request in its own audit log.
  • The district can drop any scope or remove the admin altogether, at any time, from its own /admin. Opting out leaves a working district.

Risks and mitigations
  • R1: an Access bypass path leaves an endpoint unauthenticated. Every route under /api/m, /api/pair and /api/ops must pass a credential check before its handler runs (one middleware), and a generated test calls every route with no credential and expects 401.
