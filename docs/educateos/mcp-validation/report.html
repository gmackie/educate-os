LMS-lite MCP vs Google Classroom

A school's own MCP server, deployed on Cloudflare from the launch-educate-os CLI, validated live on two production districts. Northfield runs the native LMS-lite. Harbor's classes and grades come from real Google Classroom courses on the gedu.demo.educateos.io tenant. All accounts and students are synthetic.

ShippedFull LMS-lite MCP server85 tools, built-in OAuth 2.1 with no outside identity provider, personal tokens, and an approval queue in the admin and teacher UIs. PRs #443, #444, #447.
Validated liveBoth districts, end to endA real OAuth connect, reads, drafts, queued writes approved by the teacher, the student's view, and refusals.
Bottom lineNative LMS-lite does more over MCPOver Google Classroom, MCP reads Classroom's roster and grades live, but anything an AI client authors stays in EducateOS. Google's API rules limit what can be written back.
What was compared

Three ways an AI client can reach a class

A. EducateOS LMS-lite (Northfield). The district Worker is the system of record. Its /mcp endpoint exposes the whole LMS: classes, rosters, modules, pages, activities, assignments, submissions, feedback, gradebook, quizzes, discussions, announcements and planner.

B. EducateOS over Google Classroom (Harbor). It's the same server and tool catalog. The roster is imported from Google Classroom, Classroom grades are read live, and approved grades are returned to Classroom through the passback gate.

C. Google Classroom API on its own. This is what a district would have if an AI client talked to Classroom directly with Google OAuth. It is shown from Google's documented rules (cited in docs/educateos/integrations/google-classroom.md), not from a live client.

Limitations

What each one can't do yet

A · LMS-lite (Northfield)

  • The catalog has 85 tools, including directory tools such as create_school. A teacher's class-scoped delegation refuses them (not-found), but a district admin's district-wide delegation can queue them.
  • Grades proposed over MCP wait for another approver. The official grade is never set over MCP.
  • No external client has used it yet. The client in this validation was a scripted OAuth client using the same calls Claude Code makes, not the Claude or ChatGPT apps.
  • Access tokens last 10 minutes. Refresh tokens last until the delegation ends, which is at most 90 days.

B · Over Classroom (Harbor)

  • Announcements, quizzes, modules and discussions an AI client authors appear in EducateOS, not in Classroom.
  • Grade return covers only coursework EducateOS created ([educateos-approved] titles). Assignments a teacher made in the Classroom UI can be read, but not graded.
  • Rubric scores stay in EducateOS. Only the total reaches Classroom.
  • The roster comes from a complete sync on a schedule (Classroom has no change feed), so a dropped student disappears at the next sync.

C · Classroom API alone

  • An app can modify only the coursework its own Cloud project created (@ProjectPermissionDenied).
  • There is no class-level scoping, no approval queue and no audit of what the AI did.
  • Classroom has no terms, schools or grade bands, and no discussions, modules, quizzes engine or planner.
  • Sensitive scopes need Google verification, and under-18 accounts need the admin to trust the app.

Found and fixed while validating

Problems found in production and the security review

IssueEffectFix
Metadata-document clients weren't checkedAn attacker could reuse a real client's URL with their own redirect and take the code.The document is fetched over HTTPS only, with no redirects, a 5 s timeout and a 5 KB limit, and the redirect must be one it lists (#443).
Refresh-token replayA stolen refresh chain stayed usable.A replay revokes the delegation, and client_id is required (#443).
Revoked personal token came backA race on the last-used update undid the revoke.An atomic touch() skips revoked tokens (#443).
Student-visible "drafts"Page edits, quiz edits, topics and weekly notes skipped the approval queue.Reclassified as writes, so they queue (#443).
Assets answered /mcpThe single-page app answered the OAuth metadata, and POST /mcp returned 405 in production.Added to the Worker's run-first routes for production, the demo districts and releases (#444).
A confirmed publish was refusedA teacher's own approval ran under the client's delegation, which can never publish.A confirmation now applies under the person's own authority (#447).
For a school owner

Setting it up

  1. Run npx launch-educate-os with a Cloudflare account. The wizard writes the district's config, and MCP is on by default (mode: "builtin", drafts allowed).
  2. The installer exempts /mcp, the OAuth metadata, JWKS, register, token and revoke paths from Access. /oauth/authorize stays behind it.
  3. Teachers open /teach/#/mcp and admins open /admin/#/mcp. There they copy client setup, mint personal tokens, revoke connections and approve queued writes.
  4. An existing install runs npx launch-educate-os mcp enable. Adding --strict-writes queues drafts too.
claude mcp add --transport http educateos https://<your district>/mcp
