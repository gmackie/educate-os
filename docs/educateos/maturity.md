# EducateOS capability maturity

- Status: Living document. Update a row in the PR that changes its evidence.
- Date: 2026-10-31 (rows for the MCP server, school tools, approvals, district application, identity links, installer and AI guard refreshed by SCHO-313; MCP server row by SCHO-174)
- Issue: SCHO-168 ([ADR-0011](adr/0011-open-source-charter-and-module-ownership.md), [RFC 0002](rfc/0002-integration-fabric.md) §1)

Having specification-shaped code is not the same as interoperating with a real platform. This page
records, per capability, how far the code has actually got, so that docs, READMEs and release
notes claim only what the evidence supports. The pilot gate's MET/NOT MET table
([pilot-gate.md](pilot-gate.md)) is generated from its own criteria and is not repeated here.

**No 1EdTech certification is claimed for any part of EducateOS.** Where this repository says it
supports "LTI 1.3" or "LTI Advantage", it means Tool-side code that passed the live runs against a
current Canvas and Moodle 4.5 recorded in [integrations/canvas-lti.md](integrations/canvas-lti.md)
and [integrations/moodle-lti.md](integrations/moodle-lti.md), not 1EdTech conformance-suite or
certified behaviour.

## Levels

Each level includes the ones before it.

| Level | Meaning |
| --- | --- |
| Designed | An ADR, RFC or spec describes it. No code. |
| Implemented | Code exists and type-checks. |
| Unit-tested | Package tests cover the behaviour, including failure paths. |
| Harness-tested | Exercised end to end in process, against in-process fakes, the synthetic districts or a `workerd` test pool. |
| Deployed | Runs from a release in a real Cloudflare account. |
| External-conformance-tested | Passed runs against a real external party: an LMS sandbox, a real MCP client, a OneRoster provider, or an official test suite. |
| Certified | Formally certified by the standard's body (for example 1EdTech). |

## Assessment SDK Gadget bridge

The Assessment SDK now connects immutable public Workshop Git releases to teacher-pinned class
assignments and the existing AssessmentService/AssessmentCi workflow. The Teacher Studio screens
use the real district API for pinning, evidence, provenance and review. Local Node and workerd
harnesses cover the separate Blueprint, Gatekeeper and district boundaries; this is **Harness-tested**,
not deployed or externally certified. See [workflow and limitations](assessment-gadget-workflow.md).
Owner-private committed Gadgets can stage source through the configured school Gatekeeper and,
after explicit Workshop approval, persist immutable district artifacts and SubmissionSnapshots.
A named Workshop release service verifies actual Git packs; the district independently verifies
source SHA-256, exact release commit, public assessment and its local signed rubric. The reverse
binding is installer opt-in and missing/unavailable verification blocks pinning and submission.
The separate real workerd boundaries and synthetic district workflow are tested; one deployed
browser-to-Gadget-to-Gatekeeper-to-district roundtrip is not. Arbitrary source cannot be proven free
of embedded secrets: conservative export refusal plus exact source review is required. No
production untrusted-code executor, independent-human-authorship claim or automatic grade is added.

## Provider fakes

`packages/educateos-provider-fakes` (SCHO-201) holds in-process fakes of the providers EducateOS
integrates with, built from each vendor's published API documentation: OIDC identity providers
(Clever, ClassLink, Google), the Clever Data API v3.1, OneRoster 1.2 REST with the ClassLink OAuth2
profile, the Google Classroom API, and Canvas- and Schoology-flavoured LTI 1.3 platforms. They
serve synthetic seed data and inject faults (outage, rate limit, malformed record, large removal).
The OneRoster REST sync, the LTI broker with AGS and NRPS, the Google Classroom connector client and
the Google Classroom district sync run unchanged against them, and the ClassLink connector (SCHO-204) was
built against them.

A run against a fake is Harness-tested evidence at most. It is never External-conformance-tested
evidence: a fake encodes our reading of the documentation, not the vendor's behaviour. Only the
two Clever rows, Google Classroom district sync (SCHO-77, Harbor end to end in process) and the
ClassLink row rest on the fakes. The first three stop at Harness-tested; the ClassLink row is held
at Implemented until a ClassLink account exists to test against. The package README lists what each fake does not model.

## Rules for claims

- A README or release note names the level from this table, not a stronger one.
- "Supports X" with no qualifier means at least External-conformance-tested. Below that, say
  "implements X (unit-tested)" or similar.
- A level goes up only in the PR that adds the evidence, and that PR updates this table.
