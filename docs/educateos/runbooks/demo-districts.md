northfield is the schoolos.gmac.io instance's own district, which has served
`northfield.educateos.io` as an alias since SCHO-207 (see the
[production runbook](production-instance.md#the-district-lms-lite)). It is not redeployed here, and
its data is the demo co-op's, not the Northfield fixture's.

The other five are each a separate installation of the district Worker: their own Worker name, so
their own Durable Object namespace and storage, their own Access application and audience, and their
own ForgeGraph app. They share only the code and the account. Each one's only hostname is
`<slug>.educateos.io`, a Workers custom domain, and that hostname is also its identity
(`LTI_TOOL_ORIGIN`). Because Wrangler detaches any custom domain a deploy does not list, a demo
config lists only its own hostname, and `production-config.test.ts` holds each Worker name.

They were not installed with the installer. `@educateos/installer` installs a whole instance
(router, backend and gatekeepers) with the district Worker as a backend service. Its managed
hostname aliases the router, and it needs a district-owned `baseDomain` outside educateos.io. SCHO-243
is the follow-up to make it install a district Worker at a managed hostname. When
that and the guided flow (SCHO-206) land, re-run one demo district through the guided flow.

cedarvalley offers the "Clever (EducateOS demo)" login method at Access, but the district resolves
every sign-in as an Access subject: Clever SSO in the district (`DISTRICT_CONFIG.cleverSso`, SCHO-203)
is off. Turning it on refuses any person's sign-in without Clever's claims, which would lock out the
one-time PIN administrator and test identities. The login method does not yet pass
`multi_role_user_id`, so only students could sign in. Its live Clever IDs would also not match a
roster synced from the Clever fake. The seed already trusts `https://clever.com`, so it can be
turned on later without reseeding.

The ClassLink and district OIDC sign-ins have no live identity provider. riverbend and lakeshore use
the one-time PIN until one exists (SCHO-204, SCHO-211).

## Access

The Access applications are listed in the table below. Each district's own application lists these
reusable policies, in order: the owner (`me-gmail`), `SchoolOS demo testers` (the agents' test
identities), the district's vendor sign-in where it has one (`EducateOS demo Clever accounts`, which
requires the Clever login method; `EducateOS demo Google accounts`).

| Application | Covers |
|---|---|
| `EducateOS demo district: <Name> (<slug>.educateos.io)` | the hostname; its audience is the district's `CF_ACCESS_AUD` |
| `EducateOS demo districts health (bypass)` | `<slug>.educateos.io/healthz` for all five |
| `EducateOS demo districts LTI 1.3 Tool (bypass)` | `/lti/login`, `/lti/launch`, `/lti/jwks`, `/lti/deep-link` and `/lti/register` on all five |

The Access applications must exist before a district's first deploy. That deploy attaches its custom
domain, and a hostname that no application lists would serve without Access.

Automation (the SCHO-205 live suite) signs in as the agents' test identities with a one-time PIN,
as on schoolos.gmac.io. A district administrator adds each one under "Manage classes and people".
An Access service token would pass Access, but the district's `/api` surfaces answer only people
(`SURFACE_KINDS` in `@educateos/district-app`), so no service principal is seeded. The service token
"EducateOS demo districts automation (SCHO-205/210)" is for the provider fakes' admin endpoints. Its
client ID and secret are in the operator's Keychain as `educateos-demo-districts-service-token`,
never in this repository.

## Secrets (per app, stage `production`)

| Secret | Value |
|---|---|
| `DISTRICT_CONFIG` | `node packages/educateos-district-worker/scripts/demo-district-config.ts <slug> --admin-subject <operator's Access user_uuid>`, piped into `FG_APP=educateos-<slug> forge secret set DISTRICT_CONFIG --stage production --stdin` |
| `CF_ACCESS_AUD` | the district application's audience (one; no Workshop instance is in front of these) |
| `CF_ACCESS_ISS` | `https://gmacko.cloudflareaccess.com` |

Always set these with `FG_APP=educateos-<slug>`, because `forge secret set` takes its app from
`FG_APP` or the repository link. From the repository, a demo seed would otherwise land on another
app. On `educateos-district`, the next deploy would sync it onto `schoolos-district-worker`, which
would then route to an empty Durable Object.

The seed is the fixture's district and its administrator plus the automation, and nothing else. A
whole fixture directory is over the 5 KB a secret holds. The district trusts only the Access team,
because behind Access every sign-in carries the team's issuer and the person's Access subject. The
seed is read on the object's first start only; changing it later changes nothing but the district ID
check.

A roster import links the people it creates under the first trusted issuer, the Access team, with
their roster `username` as the subject. Access subjects are UUIDs, so a rostered person signs in
only after an administrator links their Access subject (the sign-in ID the district shows them).

## ForgeGraph

For each slug: app `educateos-<slug>`, linked to `gmackie/educate-os`, stage `production`, one
`cloudflare-workers` target on hetzner-fg. Its target config:

- `workerName`: `educateos-<slug>-district`
- `appDir`: `packages/educateos-district-worker`
- `configPath`: `packages/educateos-district-worker/wrangler.demo-<slug>.jsonc`
- `buildCommand`: the district's build from the
  [production runbook](production-instance.md#build-and-deploy), with
  `stamp-commit.ts wrangler.demo-<slug>.jsonc`
- `deployCommand`: `pnpm exec wrangler deploy -c wrangler.demo-<slug>.jsonc`
- `syncSecrets: true`
- `healthCheckUrl`: `https://<slug>.educateos.io/healthz`

Create the targets only once the configs are on `main`. Every merge deploys every target, and a
target whose config file is missing fails each of those deploys. Kanbanger delivery receipts come
only from the repository's primary app (`educate-os`), not from these.
