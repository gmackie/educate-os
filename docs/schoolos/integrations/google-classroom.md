# Google Classroom provider

- Status: Research and implementation plan, 2026-10-21. No Google API has been called. Every claim
  cites Google's public documentation as read that day.
- Issue: SCHO-77 (follow-up of SCHO-27, roadmap I02).
- Code it targets: `ClassroomProvider` in `packages/schoolos-lti/src/classroom.ts`.

## Where SchoolOS stands

`@schoolos/lti` ships the Classroom adapter shell:

- `ClassroomAdapter` projects a Classroom roster into a `RosterProjection`, keyed by the identity
  `(district, https://accounts.google.com, <Google user ID>)`.
- `ClassroomGradeSink` publishes approved grades through the passback gate.

Both talk to Google only through `ClassroomProvider`, which nothing implements yet:

```ts
interface ClassroomProvider {
  listRoster(courseId: string): Promise<readonly ClassroomRosterEntry[]>;
  listCourseWork(courseId: string): Promise<readonly ClassroomCourseWork[]>;
  setAssignedGrade(input: { courseId; courseWorkId; userId; assignedGrade }): Promise<void>;
}
```

The real provider is gated on two things this page sets out: verified Google API access, and the
coursework-ownership rule.

## API access requirements

- **A Google Cloud project.** "You must use a Google Cloud project to manage a Google Classroom
  integration", and "You don't need to use any paid Google Cloud features to use Classroom API."
  <https://developers.google.com/workspace/classroom/guides/onboarding/prerequisites>
- **One project per deployment.** Tokens are bound to their project: "Access tokens generated by
  another Google Cloud project are denied by the Classroom API."
  <https://developers.google.com/classroom/faq>. Coursework is bound to its project too (see below),
  so each SchoolOS deployment that grades in Classroom has one long-lived project. Its OAuth client
  must never be swapped.
- **Who owns the project** is a decision for SCHO-77. If the root registers one project for every
  district, districts are coupled to the root (ADR-0001). If each district registers its own,
  every district goes through Google's verification. See "Decisions" below.
- **A demo domain for testing.** Testing Education behaviour needs one, named
  `gedu.demo.<yourdomain>`. It starts with Education Fundamentals, and on request comes with ten
  Education Plus licenses. Those licenses are needed for add-ons, grading periods and rubrics.
  <https://developers.google.com/workspace/classroom/guides/onboarding/prerequisites>
- **Per-user features.** Some features depend on the user's license. Check with
  `userProfiles.checkUserCapability` before a gated call.
  <https://developers.google.com/workspace/classroom/guides/key-concepts/user-eligibility>

### What each district's Google admin must do

- **Turn on Classroom data access.** Apps, then Google Workspace, then Classroom, then Data access:
  "allow users to grant access to their Classroom data". It can be set per organizational unit.
  When it is off, calls fail with `ClassroomApiDisabled`.
  <https://support.google.com/edu/classroom/answer/6250906> and
  <https://developers.google.com/workspace/classroom/troubleshooting/common-errors>
- **Configure the app for under-18 users.** "Users designated as under 18 by the age-based access
  setting are blocked from using unconfigured third-party apps." The admin sets the app to Trusted,
  Limited, Specific Google data or Blocked, and collects parental consent where the law requires it.
  <https://knowledge.workspace.google.com/admin/getting-started/editions/manage-access-to-unconfigured-third-party-apps-for-users-designated-as-under-18>
- **Plan for Trusted.** Trusted is "access to all Google Workspace services (OAuth scopes),
  including restricted services". Limited is "only access unrestricted services"
  (<https://knowledge.workspace.google.com/admin/apps/control-which-apps-access-google-workspace-data>).
  The docs don't say which tier Classroom falls in, so plan for the district marking the SchoolOS
  client **Trusted**.

SchoolOS needs no student token for the planned scope, because every call is a teacher's. Even so,
the client must be configured for the domain.

## OAuth scopes

The provider needs only these, all under `https://www.googleapis.com/auth/`
(<https://developers.google.com/workspace/classroom/guides/auth>,
<https://developers.google.com/identity/protocols/oauth2/scopes>):

| Scope | Used for | Provider method |
| --- | --- | --- |
| `classroom.rosters.readonly` | `courses.teachers.list` and `courses.students.list` | `listRoster` |
| `classroom.coursework.students` | Create the coursework SchoolOS grades. List it. Patch `assignedGrade`. Return submissions. | `listCourseWork`, `setAssignedGrade`, and a new `createCourseWork` |
| `classroom.courses.readonly` | Let the teacher pick a course when connecting an offering | the connect flow, not the provider |
| `openid` | Link a teacher's Google identity, using the OIDC `sub` | the identity-linking flow |

**Not requested:**

- `classroom.profile.emails`: email is display metadata in SchoolOS (ADR-0003), and the roster
  needs only user IDs.
- `classroom.profile.photos`, guardian, announcement and topic scopes.
- The add-on scopes.

**Sensitivity.** Google's pages label only the add-on scopes as sensitive
(<https://developers.google.com/workspace/classroom/add-ons/developer-guides/review-process-overview>).
No Classroom scope was found labelled restricted. Assume the scopes above are **sensitive**, and
confirm on the Cloud Console's Data Access page, which shows each scope's tier.

## Verification

Google's verification applies to any app with external users:

- **Brand verification.** The homepage must be on a domain verified in Search Console, and it "can
  not be only a login page". The privacy policy must be on the same domain and explain how the app
  "accesses, uses, stores, and/or shares Google user data".
  <https://support.google.com/cloud/answer/13464321>
- **Sensitive-scope verification.** It needs:
  - a use case;
  - a demo video showing the consent screen with "the same exact scopes you are requesting";
  - compliance with the Limited Use policy;
  - a justification of "why narrower scopes would not work".

  Google says this "typically takes 3-5 business days". Developer reports describe several weeks.
  <https://developers.google.com/identity/protocols/oauth2/production-readiness/sensitive-scope-verification>
- **Restricted-scope verification.** This adds an annual CASA security assessment. It is not needed
  if, as expected, no scope above is restricted.
  <https://developers.google.com/identity/protocols/oauth2/production-readiness/restricted-scope-verification>
- **Exemptions.** An *Internal* app, "used only by people in your Google Workspace or Cloud Identity
  organization", is exempt. That fits a district that registers its own project in its own Workspace
  organization, and does not fit a root-owned multi-district client (same page).
- **Testing.** Testing status allows a capped list of test users, with short-lived refresh tokens.
  That is enough for the demo-domain work in the plan below.

### Partner programs

They are optional. Google's partner pages
(<https://developers.google.com/workspace/classroom/guides/partnerships>) describe Partner Advantage
Build, which needs one integration, and the Education Integrated Solutions Initiative, which needs
at least three integrations, no ads or student purchases, and COPPA/FERPA compliance. **Neither is
required to use the Classroom API.** Add-ons are separate. They need Marketplace approval as well as
OAuth verification ("2-3 weeks"), domain allowlisting, and Teaching & Learning or Education Plus
licenses (<https://developers.google.com/workspace/classroom/add-ons>,
<https://developers.google.com/classroom/faq>), so they are out of scope here.

## The coursework-ownership constraint

This rule shapes the whole design:

- `courseWork.create`: created coursework and its submissions are "associated with the Developer
  Console project of the OAuth client ID used to make the request", and later changes "must be made
  with an OAuth client ID from the associated Developer Console project".
  <https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork/create>
- `studentSubmissions.patch`: "This request must be made by the Developer Console project of the
  OAuth client ID used to create the corresponding course work item or an add-on attachment with
  Grade Sync enabled on the corresponding course work item."
  <https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/patch>
- `studentSubmissions.return` has the same rule.
  <https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions/return>
- **The FAQ.** "Typically, an application can only modify work that it creates."
  <https://developers.google.com/classroom/faq>
- **The error.** `ProjectPermissionDenied` (403) "indicates that the request attempted to modify a
  resource associated with a different Developer Console project". Its message starts with `@`; match
  on `"@ProjectPermissionDenied "`.
  <https://developers.google.com/workspace/classroom/troubleshooting/common-errors>,
  <https://developers.google.com/workspace/classroom/troubleshooting/error-structure>
- **`associatedWithDeveloper`.** It is read-only and is on CourseWork and StudentSubmission:
  "Whether this course work item is associated with the Developer Console project making the
  request." <https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork>

Consequences for SchoolOS:

1. **A gradebook column is coursework SchoolOS created.** A teacher can't point SchoolOS at an
   assignment made in the Classroom UI. When an offering's activity is connected, SchoolOS creates the
   coursework itself, through the teacher's token, and records its ID on the grade route.
2. **`listCourseWork` returns only owned coursework.** It keeps items with
   `associatedWithDeveloper: true` and drops the rest. Then `ClassroomGradeSink.check` refuses
   anything else before passback, instead of failing at Google.
3. **The project is permanent.** Changing the OAuth client's project orphans every column. The
   project ID is pinned in the district's configuration, and a change is refused while any Classroom
   grade route exists.

## Grading semantics

- **The grade fields.** `assignedGrade` "may be modified only by course teachers". `draftGrade` is
  "only visible to and modifiable by course teachers". Both are non-negative and rounded to two
  decimal places.
  <https://developers.google.com/workspace/classroom/reference/rest/v1/courses.courseWork.studentSubmissions>
- **The patch call.** `studentSubmissions.patch` needs `updateMask`. Teachers may set `draftGrade`
  and `assignedGrade`.
- **Return.** Unlike the Classroom UI, `return` "does not set assignedGrade to the draftGrade
  value", so SchoolOS sets `assignedGrade` first and then returns the submission.
- **Rounding.** SchoolOS publishes only teacher-approved grades. A grade with more than two decimal
  places is refused rather than rounded, because rounding would publish a number the teacher never
  approved. This matches the existing refusal of a differing `maxPoints`.
- **Rubrics.** "student submissions can't be graded with a rubric by the API"
  (<https://developers.google.com/workspace/classroom/rubrics/getting-started>), so SchoolOS rubric
  results stay in SchoolOS. Only the total goes to `assignedGrade`.

## Identity

- **The OIDC issuer.** It is "Always `https://accounts.google.com` or `accounts.google.com`". `sub`
  is "unique among all Google Accounts and never reused". And: "Don't use the `email` field as a
  unique identifier".
  <https://developers.google.com/identity/openid-connect/openid-connect>.
  `CLASSROOM_ISSUER` is the `https://` form. A linking flow must normalize the bare form to it.
- **Classroom's user ID.** Classroom's `userProfiles.id` is only described as "Identifier of the
  user" (<https://developers.google.com/workspace/classroom/reference/rest/v1/userProfiles>). **Google
  does not document that it equals the OIDC `sub`.** The provider must not assume it does. When a
  person links Google, SchoolOS records the OIDC `sub`, then calls `userProfiles.get("me")` with the
  same token. It stores the link only if the two IDs are equal. If they aren't, the link is refused
  and the case is reported. `ClassroomAdapter` keys roster entries on the Classroom user ID, so this
  check is what makes the roster match the linked principals.

## Quotas and change notification

- **Quotas.** 4,000,000 queries a day per client, 3,000 a minute per client and 1,200 a minute per
  user, measured as a 60-second moving average. Over the limit, Google returns `RESOURCE_EXHAUSTED`.
  Back off exponentially.
  <https://developers.google.com/workspace/classroom/limits>
- **Push notifications.** Roster changes can come by push through Cloud Pub/Sub
  (`registrations.create` with `COURSE_ROSTER_CHANGES`), with the `classroom.push-notifications`
  scope. A registration "lasts a week" and must be renewed.
  <https://developers.google.com/workspace/classroom/guides/push-notifications>.
  Pub/Sub sits outside the district's Cloudflare account, so the first version polls on the
  existing roster-sync schedule and does not use push.

## Implementation plan

The steps go in order. Steps 1-4 can be built and tested now against a fake Google HTTP surface. Steps
5-7 need the project and verification.

1. **Extend the interface.** Add to `ClassroomProvider`:
   - `createCourseWork(input: { courseId, title, maxPoints }): Promise<ClassroomCourseWork>`
   - `returnSubmission(input: { courseId, courseWorkId, userId }): Promise<void>`

   Change `listCourseWork` so it promises only coursework the provider's project owns. The fake in
   the `@schoolos/lti` tests gains the ownership rule: patching unowned coursework throws
   `forbidden`, as Google's `ProjectPermissionDenied` would.
2. **Build `GoogleClassroomHttpProvider`.** It goes in a new `@schoolos/integrations` namespace,
   `google-classroom`, over an injected `fetch` and a `TokenProvider` for the teacher's access token.
   Every response is parsed with Zod. Unknown fields are stripped, not rejected, because Google adds
   fields. Errors become `SchoolOsError`:
   - `ProjectPermissionDenied` maps to `forbidden`;
   - `ClassroomApiDisabled` maps to `unavailable`, with an operator action telling the district to
     turn on Classroom data access;
   - `RESOURCE_EXHAUSTED` maps to `unavailable` and is retried with backoff.

   Rosters page through `courses.students.list` and `courses.teachers.list` using `nextPageToken`.
   `setAssignedGrade` calls `studentSubmissions.list?userId=` and then `patch` with
   `updateMask=assignedGrade`. A grade that isn't a multiple of 0.01 is refused.
3. **Add the teacher-token store.** OAuth refresh tokens are kept in the district's account as Worker
   secrets or encrypted DO storage, per teacher, and never leave it (ADR-0001). The kernel already
   has a Google gatekeeper (`packages/gatekeeper-google`) whose credential handling may be reusable
   through its connect flow. Check that before writing a new one, and get kernel review if the
   gatekeeper needs Classroom scopes added.
4. **Link identities.** Add `openid`-based linking with the `sub` equals `userProfiles.id` check
   above, through `@schoolos/identity`'s admin-confirmed linker. A link to issuer
   `https://accounts.google.com` is accepted only if the district lists that issuer in
   `trustedIssuers`.
5. **Set up the project** (needs the decision below). Register the Cloud project, enable the
   Classroom API, configure the consent screen with the four scopes, and use a demo domain with
   Education Plus licenses for testing.
6. **Verify** (needs Google). Complete brand verification and sensitive-scope verification: a demo
   video, a privacy policy on the verified domain, and the justification for each scope.
7. **Run the pilot runbook.** A district admin turns on Classroom data access, configures the client
   as Trusted for staff OUs, and connects one offering. Check four things:
   - the coursework created by SchoolOS appears;
   - a roster sync projects the class;
   - an approved grade arrives as `assignedGrade`;
   - patching a teacher-made assignment is refused locally.

## Decisions SCHO-77 still needs

1. **Who owns the Google Cloud project.**
   - (a) The root owns one verified client for all districts. Districts verify once; it couples
     districts to the root's project, and losing it orphans every district's columns.
   - (b) Each district registers its own project as an *Internal* app, which is exempt from
     verification. It needs district admin effort, keeps ADR-0001's root independence, and puts the
     project ID in district config.

   (b) is the better fit for ADR-0001. (a) is easier to onboard.
2. **Whether to accept the deployment's one-project-forever constraint** at install, with a refusal
   to change it while any Classroom grade routes exist.
